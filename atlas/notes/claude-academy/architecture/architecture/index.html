Human–Agent Team — архітектура

Версія 1.0.0 · 2026-11-22 · проєктна рекомендація

Рішення для FITGYM CRM. Почати зі звіту готовності релізу. Людина формулює мету й вирішує, чи приймати результат. Orchestrator збирає докази з дозволених ресурсів, запускає перевірки й повертає одну версіоновану чернетку. Перший пілот не потребує прав на production, запису в GitHub або доступу до даних клієнтів.

Джерело істини для виконання — транзакційна БД. Стан задачі: queued → planning → running → validating → succeeded. Схвалення окремої дії переводить крок у waiting_approval. Блокер, провал бюджету або скасування мають явні стани. Перехід кроку на running використовує lease із fencing token. Застарілий worker не може записати результат після перевидачі lease.

Планування, виконання й відновлення

Відомий релізний процес стартує як детермінований DAG: прочитати PR і CI паралельно, синтезувати звіт, перевірити докази, передати людині. Динамічна декомпозиція з’являється лише після порівняння з базовим DAG. Планувальник пропонує кроки, а контролер перевіряє scope, глибину та дозволи. Воркери створюють окремі артефакти. Інтегратор відповідає за єдиний результат і розбіжності.

Для зовнішнього виклику спочатку збережи намір і стабільний idempotency key. Фіксуй dispatch через outbox. При timeout після можливого запису спочатку перевір outcome у провайдера. Коли провайдер не підтримує ключ або безпечну звірку, переведи в needs_reconciliation. Тимчасові збої читання повторюй з обмеженим backoff. При помилці політики, даних чи браку бюджету завершуй крок явним статусом. При cancel зупини нові кроки й зафіксуй уже виконані дії.

Спільна пам’ять

Канонічні рішення мають власника, version і evidence. Task state, чернетки моделі й затверджені факти зберігаються окремо. Контекст воркера містить мінімальні refs. RAG фільтрує tenant і ACL перед пошуком, застосовує lexical + vector із дедуплікацією, повертає версію й URL. Чернетка агента потрапляє в shared knowledge після review. Журнал audit зберігає події та digests. Сирі відповіді інструментів підлягають обмеженню доступу й строку зберігання.

Права та бюджет

Ролі отримують allowlist. Read-only джерела працюють у встановленому scope. Запис у зовнішню систему, merge, production deployment, зміна політики та доступу потребують дії людини або обмеженого схвалення для конкретного payload. Gateway перевіряє це незалежно від моделі. Зміна payload чи expiry скасовує схвалення. Зовнішній контент є даними для аналізу. Текст у документах чи tool responses не впливає на дозвіл.

Перший експериментальний ліміт для релізного звіту: 2 паралельні readers, 12 tool calls, 20 000 input / 4 000 output токенів на задачу, 120 секунд і 1 повтор read step. Перед паралельними викликами резервуй бюджет атомарно та звіряй з фактичним usage. Тримай окремий резерв на перевірку й синтез. На межі ліміту поверни підтверджені результати й список пропусків. Пороги пілоту перевірити на реальних задачах.

Приймання

Перевіряй структуру звіту, актуальність commit SHA, відповідність доказів, відсутність недозволеного запису та явне позначення неповноти. Людина приймає релізне рішення. Мінімальні перевірки у Agent-Evaluation.md.
